> Created: 2026-02-12
> Status: **IMPLEMENTED**
> Implementation: `src/preLVS/export/frontend_json.jl`

---

## Background

### The Problem

The laygo3-frontend needs two pieces of information to visualize a layout with net highlighting:

1. **Layout JSON** — geometry of metals, vias, pins (already exists, generated by laygo3 Python via `DesignExporter`)
2. **LVS JSON** — which metals/vias are electrically connected (generated by preLVS)

The frontend renders rectangles from the layout JSON. When the user clicks a metal, the frontend needs to highlight all electrically connected metals and vias. This connectivity information comes from preLVS.

### Why preLVS Generates This File

- **laygo3 (Python)** cannot be modified — it's a separate repository
- **preLVS** already computes exactly the connectivity information needed (via BFS on the merged metal graph)
- preLVS reads the same layout JSON that the frontend will render, so the geometry is consistent

### The Matching Challenge

The layout JSON from laygo3 has **no IDs** on elements. Metals are anonymous:
```json
{"xy": [[0, 0], [12090, 0]], "layer": "M2", "hextension": 75, "vextension": 75}
```

preLVS assigns its own internal IDs (`MOVector.idx`) during merge, but these IDs don't exist in the layout JSON.

**Solution**: The LVS JSON includes the **raw metal geometry** (before merging) alongside the component assignment. The frontend matches its rendered elements to LVS elements using geometry. Since all coordinates are integers (semiconductor grid units), exact matching works after the frontend applies extensions to its layout JSON coordinates (see [Frontend Matching](#how-the-frontend-matches)).

## Core Logic: Propagating Component IDs to Raw Metals

The key challenge: component IDs are assigned to **merged metals** (MOVectors), but the frontend needs component IDs on **raw metals** (MVectors) to match against the layout JSON.

### How Merging Works

In `merge_mvector_list()` (new_metal.jl): multiple `MVector`s at the same `(layer, p_coord)` that overlap in the secondary coordinate get merged into one `MOVector`. The `MOVector` gets a unique `.idx`. The original `MVector` objects are not explicitly tracked.

### Spatial Containment Matching

Since both raw and merged metals share `(layer, p_coord)` and the merged metal's span **contains** all its contributing raw metals' spans:

```
For each raw MVector at (layer, p_coord):
    Find the merged MOVector at same (layer, p_coord) where:
        raw_s_start >= merged_s_start  AND
        raw_s_end   <= merged_s_end

    → That merged metal's ComponentInfo.number is the component_id
```

This is implemented in `build_raw_to_component_map()`. For vias, `build_via_to_component_map()` directly extracts from `ComponentInfo.vias`.

## Important: Extension Handling

### How preLVS Stores Metal Coordinates

In `db_to_MData()` (new_metal.jl), the **span-direction extension** is baked into the `s_coord` values:

```julia
# From db_to_MData (simplified):
min_s = min(xy coords in span direction)
max_s = max(xy coords in span direction)
points = SVector{2, MPoint}(
    MPoint(min_s - span_extension, START),
    MPoint(max_s + span_extension, END)
)
width = 2 * perp_extension
```

This means **`s_coord` values in MVector already include the span extension**. The raw geometry represents the **actual physical extent** of the metal, not the centerline.

### Layout JSON vs LVS JSON Coordinates

| | Layout JSON (from laygo3 Python) | LVS JSON (from preLVS) |
|---|---|---|
| **Metal xy** | Centerline coordinates | Physical extent (extensions baked into span direction) |
| **Extensions** | Separate `hextension` / `vextension` fields | Baked into `xy` and `s_range`; `width = 2 * perp_extension` |
| **Via xy** | Center position | Same center position |
| **Via extension** | Separate `extension` field | Same `extension` field |

**Example** — a horizontal M2 metal:
```
Layout JSON: {"xy": [[0, 600], [100, 600]], "hextension": 75, "vextension": 10}
  → Physical extent: x from (0-75) to (100+75) = [-75, 175], y = 600, width = 20

LVS JSON:    {"xy": [[-75, 600], [175, 600]], "s_range": [-75, 175], "p_coord": 600, "width": 20}
  → Already represents physical extent
```

### Field Descriptions

**`metals[]`** — one entry per raw (pre-merge) metal, flattened to absolute coordinates:
| Field | Type | Description |
|-------|------|-------------|
| `layer` | `"M{n}"` | Layer name |
| `xy` | `[[x0,y0],[x1,y1]]` | Physical extent (span extension baked in). Vertical: `[[p, s_start], [p, s_end]]`. Horizontal: `[[s_start, p], [s_end, p]]` |
| `p_coord` | int | Primary coordinate (x for vertical layers, y for horizontal) |
| `s_range` | `[start, end]` | Secondary range with span extension applied |
| `width` | int | Width = 2 * perpendicular extension |
| `component_id` | int or null | Connected component ID (null if unassigned) |
| `net` | string or null | Net name from connectivity analysis |
| `laygo_origin` | string or null | Instance path traceback |

**`vias[]`** — one entry per via:
| Field | Type | Description |
|-------|------|-------------|
| `layer` | `[string, string]` | Layer pair (e.g., `["M2", "M1"]`) |
| `xy` | `[x, y]` | Center position |
| `extension` | `[int, int]` | Via extensions |
| `component_id` | int or null | Connected component ID |
| `net` | string or null | Net name |
| `laygo_origin` | string or null | Instance path traceback |

**`components[]`** — one entry per connected component:
| Field | Type | Description |
|-------|------|-------------|
| `id` | int | Component ID (1-indexed) |
| `net` | string or null | Net name (null if floating) |
| `is_consistent` | bool | False if SHORT detected (mixed nets) |

**`errors[]`** — one entry per error:
| Field | Type | Description |
|-------|------|-------------|
| `type` | string | `"SHORT"`, `"OPEN"`, or `"FLOATING"` |
| `component_id` | int | Affected component ID |
| `nets` | string[] | Conflicting nets (SHORT only) |
| `net` | string | Expected net (OPEN only) |
| `message` | string | Human-readable description |

## How the Frontend Matches

The layout JSON stores metals as centerline + separate extensions, while the LVS JSON stores the physical extent with extensions baked in. The frontend adapter must account for this difference.

### Matching Strategy

1. Parse the LVS JSON and build a geometry lookup.
2. For each metal from the layout JSON, compute its physical extent by applying the span extension.
3. Match against the LVS lookup by `(layer, extended_xy)`.

```typescript
// 1. Build lookup from LVS JSON (xy already has extensions baked in)
const metalLookup = new Map<string, { componentId: number; net: string | null }>();
for (const m of lvsData.metals) {
  const key = `${m.layer}_${m.xy[0][0]}_${m.xy[0][1]}_${m.xy[1][0]}_${m.xy[1][1]}`;
  metalLookup.set(key, { componentId: m.component_id, net: m.net });
}

// 2. For a layout JSON metal, extend xy by span extension before matching
function getComponent(layoutMetal: LayoutMetal): { componentId: number; net: string | null } | null {
  const isVertical = isVerticalLayer(layoutMetal.layer);
  const ext = isVertical ? layoutMetal.vextension : layoutMetal.hextension;

  let xy: number[][];
  if (isVertical) {
    // Vertical: span is y-direction, apply vextension
    const yMin = Math.min(layoutMetal.xy[0][1], layoutMetal.xy[1][1]) - ext;
    const yMax = Math.max(layoutMetal.xy[0][1], layoutMetal.xy[1][1]) + ext;
    const x = layoutMetal.xy[0][0];
    xy = [[x, yMin], [x, yMax]];
  } else {
    // Horizontal: span is x-direction, apply hextension
    const xMin = Math.min(layoutMetal.xy[0][0], layoutMetal.xy[1][0]) - ext;
    const xMax = Math.max(layoutMetal.xy[0][0], layoutMetal.xy[1][0]) + ext;
    const y = layoutMetal.xy[0][1];
    xy = [[xMin, y], [xMax, y]];
  }

  const key = `${layoutMetal.layer}_${xy[0][0]}_${xy[0][1]}_${xy[1][0]}_${xy[1][1]}`;
  return metalLookup.get(key) ?? null;
}

// 3. On click → highlight all metals/vias with same component_id
```

### Via Matching

Vias use the same `xy` and `extension` format in both layout JSON and LVS JSON, so matching is straightforward:

```typescript
const viaLookup = new Map<string, { componentId: number; net: string | null }>();
for (const v of lvsData.vias) {
  const key = `${v.layer.join("_")}_${v.xy[0]}_${v.xy[1]}`;
  viaLookup.set(key, { componentId: v.component_id, net: v.net });
}
```

### Hierarchical Layout Handling

The layout JSON may be hierarchical (subblocks with local coordinates). The frontend adapter must:
1. Flatten the hierarchy by recursively transforming local coordinates to absolute coordinates.
2. Apply span extensions to each metal's absolute xy.
3. Match the resulting geometry against the flat LVS JSON.

Integer coordinates ensure exact matching with no floating-point ambiguity.

## Edge Cases

| Case | How Handled |
|------|-------------|
| Raw metal not contained in any merged metal | `component_id: null`, `net: null` |
| Multiple merged metals at same `(layer, p_coord)` | Matched by s_range containment — each raw metal is fully within exactly one merged metal |
| Via not in any component | `component_id: null`, `net: null` |
| Metals beyond orientation_list range | Skipped (layer > length(orientation_list)) |
| Empty netname | `null` in JSON, not empty string |
| SHORT error (multiple nets in one component) | `is_consistent: false`, conflicting nets listed in `errors[].nets` |
